  化境期 · 设计模式
  设计模式不是背的，是理解思想、用到合适的地方
================================================================


【一、模块简介】

徒弟啊，设计模式这东西，争议挺大的。
有人奉为圭臬，有人嗤之以鼻。
师傅的看法是：设计模式是好东西，但别乱用。

什么是设计模式？简单说就是：
前辈们总结出来的，解决某类问题的
通用套路和最佳实践。

你学了设计模式，不是说写代码就要硬套模式，
而是脑子里有这些套路了，遇到类似的问题，
能快速想到"哦，这个问题用 XX 模式比较合适"。

这个模块叫"化境期"，意思就是
从"会写代码"到"会设计"的蜕变。


【二、学习目标】

学完本模块，你要能做到：

  1. 说出 11 个常用设计模式的名字和用途
  2. 理解每个模式解决什么问题、适用场景
  3. 能区分创建型、结构型、行为型三大类
  4. 看到一段代码，能识别出用了什么模式
  5. 最重要的：知道什么时候不该用模式


【三、模式列表与分类】

咱一共 11 个模式，分三大类：

【创建型模式——管对象怎么创建的】
  singleton.cpp              ← 单例模式
    核心：一个类只能有一个实例，全局访问点

  factory_abstract.cpp       ← 工厂模式 + 抽象工厂
    核心：把创建对象的逻辑封装起来，不暴露细节

  builder.cpp                ← 建造者模式
    核心：分步构建复杂对象，构建过程和表示分离

【结构型模式——管类和对象怎么组合的】
  adapter.cpp                ← 适配器模式
    核心：把一个接口转换成另一个接口，兼容不兼容的类

  decorator.cpp              ← 装饰器模式
    核心：动态地给对象添加功能，比继承更灵活

  proxy.cpp                  ← 代理模式
    核心：用一个代理对象控制对真实对象的访问

【行为型模式——管对象之间怎么交互的】
  observer.cpp               ← 观察者模式
    核心：一对多的依赖，一个变了大家都收到通知

  strategy.cpp               ← 策略模式
    核心：把算法封装成类，互相可以替换

  visitor.cpp                ← 访问者模式
    核心：在不改变类的前提下，给类增加新的操作

  state.cpp                  ← 状态模式
    核心：对象在不同状态下有不同行为，状态改变行为也变

  command.cpp                ← 命令模式
    核心：把请求封装成对象，可以排队、撤销、重做


【四、学习顺序建议】

师傅建议你这么学：

【先学创建型】
  单例 → 工厂 → 建造者
  创建型最好理解，也最常用。
  先从简单的入手，建立感觉。

【再学结构型】
  适配器 → 装饰器 → 代理
  结构型稍微抽象一点，但也不难。
  重点理解"组合优于继承"这个思想。

【最后学行为型】
  观察者 → 策略 → 命令 → 状态 → 访问者
  行为型模式最多，也最灵活。
  观察者和策略最常用，先把这俩搞懂。
  访问者最复杂，放最后看。

【学习方法】
  学每个模式的时候，先问自己三个问题：
  1. 这个模式解决什么问题？
  2. 不用这个模式的话，代码会是什么样？
  3. 用了这个模式，有什么好处？有什么代价？

  别光记 UML 图，要理解思想。


【五、核心知识点梳理】

咱挑几个最核心的模式讲讲思想：

1. 【单例模式】
   什么时候用？有些东西全局就该有一个，
   比如配置管理器、日志器、线程池。

   关键点：
   - 构造函数私有，不让外面 new
   - 提供一个静态方法获取实例
   - 线程安全的实现方式（饿汉式、懒汉式、局部静态）

   注意：单例别滥用。很多东西不是必须单例的，
   用单例反而耦合了、不好测试了。

2. 【工厂模式】
   什么时候用？创建对象的逻辑比较复杂，
   或者创建哪种对象需要根据条件决定。

   思想：把"创建对象"这件事封装起来。
   调用方不用知道具体创建了哪个类，
   也不用知道创建的细节。

   好处：新增产品的时候，只加工厂就行，
   不用改调用方的代码。符合开闭原则。

3. 【观察者模式】
   什么时候用？一个对象的状态变化，
   需要通知其他好几个对象。

   思想：发布-订阅。
   被观察者（发布者）维护一个观察者列表，
   状态变了就遍历列表，挨个通知。

   好处：被观察者和观察者之间解耦了。
   加新的观察者不用改被观察者的代码。

4. 【策略模式】
   什么时候用？同一个功能有好几种实现方式，
   需要能切换。

   思想：把每种算法封装成一个类，
   这些类实现同一个接口。
   客户端想用哪个就用哪个，随时能换。

   好处：算法可以独立变化，
   新增算法不用改原有代码。

5. 【装饰器模式】
   什么时候用？想给对象动态添加功能，
   而且功能可以叠加。

   思想：装饰器和被装饰对象实现同一个接口，
   装饰器持有一个被装饰对象的引用。
   调用的时候，先调用装饰器的逻辑，
   再调用被装饰对象的逻辑。

   比继承灵活：功能可以任意组合，
   不用搞一堆继承类。


【六、常见坑与注意事项】

1. 【为了用模式而用模式】
   这是新手最容易犯的毛病。
   学了几个模式，看什么都想套一下。
   结果简单的问题搞复杂了，代码越写越绕。

   记住：模式是工具，不是目的。
   合适就用，不合适就别硬上。

2. 【过度设计】
   什么都要抽象、都要扩展、都要模式，
   代码结构是"优雅"了，但可读性差了，
   维护成本反而更高了。

   有句话叫"YAGNI"——You Aren't Gonna Need It。
   你不会需要它的。别为了可能的扩展提前设计，
   等真需要的时候再重构也不迟。

3. 【模式不是越多越好】
   一个项目里用了十几个模式，
   不代表你水平高，可能说明你设计过度了。
   简单、清晰、好维护，才是好代码。

4. 【模式的名字不重要】
   面试的时候可能要背名字，
   但实际工作中，你知道思想、会用就行。
   叫什么名字不重要，解决问题才重要。


【七、老师傅的经验之谈】

1. 【设计模式学的是思想，不是套路】
   徒弟，这话师傅跟你说三遍：
   学思想！学思想！学思想！

   单例的思想是什么？—— 控制实例数量。
   工厂的思想是什么？—— 封装创建逻辑。
   观察者的思想是什么？—— 解耦发布和订阅。
   策略的思想是什么？—— 封装变化，面向接口。

   理解了思想，你甚至能自己"发明"模式。
   因为模式本来就是从实践中总结出来的。

2. 【过度设计比不用模式更糟】
   很多人学了设计模式之后，
   写个小项目也要套七八个模式，
   美其名曰"可扩展"、"可维护"。

   实际上呢？代码绕来绕去，
   新人接手看半天看不懂，
   出了 bug 也不好定位。
   这叫"为了设计而设计"，反而是坏事。

   师傅的原则：能简单就简单。
   先把功能实现了，等真的需要扩展了，
   再重构、再引入模式也不迟。

3. 【模式是经验的总结，不是教条】
   设计模式不是什么必须遵守的金科玉律。
   它只是前辈们踩坑踩出来的经验。
   你可以参考，可以借鉴，
   但不要被它束缚住。

   实际项目中，模式经常是"混搭"的，
   一个设计里可能融合了好几个模式的思想。
   别死抠"这到底是什么模式"。

4. 【先会写代码，再学设计】
   设计模式这东西，写代码写少了理解不了。
   你没踩过坑，就不知道模式好在哪。
   所以新手别急着学模式，
   先把代码写好，项目做多了，
   再回头看设计模式，你会恍然大悟：
   "哦！原来我上次那个问题，用这个模式就解决了！"

5. 【设计的目的是降低复杂度】
   不管用什么模式、什么架构，
   最终目的都是降低复杂度、让代码好维护。
   如果一个设计让代码更复杂了，
   那它就不是一个好设计。

   简单，永远是最高的追求。
