================================================================
                    异常与错误处理学习指南
================================================================

一、为什么要有异常？
----------------------------------------------------------------

先讲个故事，C 时代的程序员是怎么处理错误的。

C 语言没有异常，大家用返回值表示错误。比如：

    int read_file(const char* path, char* buf, int size) {
        FILE* fp = fopen(path, "r");
        if (!fp) return -1;        // -1 表示打开失败
        int n = fread(buf, 1, size, fp);
        fclose(fp);
        if (n < size) return -2;   // -2 表示读取不完整
        return n;                  // 正数表示读取的字节数
    }

看起来还行？那调用它呢：

    int result = read_file("data.txt", buf, 1024);
    if (result == -1) {
        // 处理打开失败
    } else if (result == -2) {
        // 处理读取失败
    } else {
        // 正常逻辑
    }

一层还好，要是嵌套个三五层呢？每层都要检查返回值，
正常逻辑和错误处理搅在一起，代码读起来乱七八糟。

更要命的是——人会偷懒。
"这个函数应该不会出错吧？先不检查了。"
"赶时间，回头再说。"
然后就没有然后了，bug 就这么埋下了。

异常机制就是为了解决这些问题：

  1. 错误无法忽略：不 catch 就崩，逼你处理
  2. 正常逻辑和错误处理分离：try 里写正常流程，catch 里处理错误
  3. 自动传播：底层出的错，上层统一处理，不用每层都传返回值
  4. 自带类型信息：不同的异常类型代表不同的错误，比数字错误码直观

当然，异常不是银弹，它也有代价和争议。往下看。


二、异常的代价与争议
----------------------------------------------------------------

【异常的代价】

  1. 运行时开销
     为了支持栈展开（stack unwinding），编译器要生成额外的信息。
     但现代编译器（比如 GCC 的零开销异常模型）在"不抛异常"的路径上
     几乎没有开销，只有真正抛出异常的时候才会慢。
     所以记住：异常是给"异常情况"用的，不要用来做正常流程控制。

  2. 代码体积增大
     异常表、栈展开信息……会让可执行文件变大一点。
     嵌入式开发、对体积敏感的场景可能会在意。

  3. 控制流不直观
     看到一个函数调用，你不知道它会不会抛异常、抛什么异常。
     不像错误码，看返回值就知道。
     代码的"阅读成本"会高一些。

  4. 异常安全难写
     这是 C++ 独有的痛点。
     Java 有 GC，Python 有 GC，资源不用手动管。
     C++ 要自己管内存、文件、锁……
     一旦抛异常，没处理好就泄漏了。
     写出真正异常安全的代码，需要经验和技巧。

【关于"异常该不该用"的争论】

C++ 社区对异常的态度一直有分歧：

  - 支持派（大多数）：异常是好东西，合理使用收益很大
  - 反对派（比如游戏引擎、嵌入式领域）：异常开销不可接受，禁用

两种说法都有道理，关键看场景。
游戏引擎每一帧都要卡时间，确实容不得意外。
普通业务代码，异常带来的好处远大于那点开销。

【老师傅的看法】
  大多数情况下，用异常是划算的。
  但要注意：
    - 不要在性能热点路径上用异常做正常流程控制
    - 一定要写异常安全的代码（RAII 大法好）
    - 项目里要统一风格，不要一半异常一半错误码


三、异常安全是 C++ 的必修课
----------------------------------------------------------------

什么是异常安全？
简单说：就算抛异常，也不会出问题——
不泄漏资源、不破坏数据、不崩溃。

异常安全有三个级别（从低到高）：

  1. 基本保证（Basic Guarantee）
     抛异常后，对象处于合法但不确定的状态。
     至少资源不泄漏，程序还能继续跑。
     但对象里的数据可能变了一半，不确定对不对。

  2. 强保证（Strong Guarantee）
     抛异常后，对象状态完全不变。
     就像这个函数从来没被调用过一样。
     "要么全成功，要么全失败"。
     典型实现方式：copy-and-swap。

  3. 不抛出保证（No-throw Guarantee）
     保证绝对不抛异常，一定成功。
     这是最高级别的异常安全。
     比如：基本类型运算、析构函数、swap 函数。

【为什么异常安全这么重要？】

因为异常是"隐形的返回路径"。
你写的每一行代码，理论上都可能抛异常（除非你知道它不抛）。
如果没有异常安全意识，你的代码到处都是"定时炸弹"——
平时好好的，哪天出个异常就崩了、泄漏了、数据错乱了。

C++ 里很多坑都和异常安全有关：
  - new 了对象之后抛异常，delete 没执行 → 内存泄漏
  - 加锁之后抛异常，解锁没执行 → 死锁
  - 容器 push_back 抛异常，元素加了一半 → 状态损坏
  - 析构函数抛异常 → 直接 terminate

所以说，异常安全是 C++ 程序员的基本功。
不会写异常安全的代码，就不算会 C++。


四、什么是 RAII？为什么和异常安全绑在一起？
----------------------------------------------------------------

RAII = Resource Acquisition Is Initialization
       资源获取即初始化

这名字起得太学术了，让人望而生畏。
其实就是个很朴素的思想：

  用对象管理资源。
  构造的时候获取资源，析构的时候释放资源。
  对象生命周期结束，资源自动释放。

为什么和异常安全有关系？
因为 C++ 保证：
  局部对象在离开作用域时（不管是正常 return 还是异常抛出），
  析构函数一定会被调用。

这就意味着——
只要你把资源交给对象管，不管抛不抛异常，资源都会释放。

【RAII 的例子】

标准库里到处都是 RAII：

  - std::string / std::vector
    构造时分配内存，析构时释放。
    你不用手动 new/delete。

  - std::unique_ptr / std::shared_ptr
    智能指针，管动态分配的对象。

  - std::lock_guard / std::unique_lock
    管互斥锁，构造加锁，析构解锁。

  - std::fstream
    管文件，构造打开，析构关闭。

【怎么用 RAII？】

  1. 优先用标准库的 RAII 类
     动态内存用智能指针，文件用 fstream，锁用 lock_guard。

  2. 自己写 RAII 类
     如果标准库没有的资源，自己写个类包一下。
     规则很简单：
       - 构造函数获取资源
       - 析构函数释放资源
       - 禁止拷贝（或正确实现拷贝语义）
       - 提供访问原始资源的方法（get()）

记住：在 C++ 里，手动管理资源是"低级操作"。
能用 RAII 就用 RAII，别自己 new/delete、open/close。
RAII 用得好，你的代码不仅异常安全，还更简洁。


五、最佳实践与常见陷阱
----------------------------------------------------------------

【最佳实践】

  1. 用标准异常，尽量不要抛普通类型（int、string 之类）
     大家都认识 std::exception，统一接口好处理。

  2. 按值抛，按引用捕
     throw std::runtime_error("...");   // 按值抛
     catch (const std::exception& e) { }  // 按 const 引用捕
     这样避免对象切片和不必要的拷贝。

  3. catch 的顺序：从具体到通用
     先捕获子类异常，再捕获父类异常。
     不然父类的 catch 会把子类的都抢走。

  4. 不要空 catch（吞掉异常不处理）
     catch (...) { } 然后啥也不干？
     那你还不如不 catch，让程序崩了还好排查。
     真要吞，至少记条日志。

  5. 析构函数不要抛异常
     这个说了八百遍了，记住就行。
     真要清理可能出错，在析构函数内部 try/catch 掉。

  6. 移动构造、移动赋值、swap 尽量标 noexcept
     对性能影响很大，尤其是容器里的元素。

  7. 异常要带足够的信息
     what() 里写清楚哪错了、为什么错，方便排查。
     自定义异常可以加错误码、文件名、行号等信息。

  8. 不要用异常做流程控制
     异常是给"异常情况"用的。
     正常的业务逻辑（比如用户输入不合法），
     用返回值或者状态机更合适。

【常见陷阱】

  陷阱 1：构造函数抛异常，资源泄漏
    原因：构造函数抛异常时，析构函数不会被调用。
    解决：成员都用 RAII，不要裸指针。

  陷阱 2：析构函数抛异常
    原因：栈展开时再抛异常 → std::terminate
    解决：析构函数里 try/catch 掉，只记日志。

  陷阱 3：new 了之后抛异常
    原因：new 和 delete 之间有代码抛异常，delete 没执行
    解决：用智能指针，别手动 new/delete。

  陷阱 4：加锁后抛异常
    原因：lock 和 unlock 之间抛异常，unlock 没执行 → 死锁
    解决：用 lock_guard / unique_lock。

  陷阱 5：异常规格说明（throw() / throw(int, string)）
    注意：C++11 之后动态异常规格已经被废弃了！
    现在只用 noexcept。
    看到 throw() 就当成 noexcept 来理解。

  陷阱 6：在回调函数里抛异常
    C 语言的回调、信号处理函数……
    异常不好跨 C 边界，行为未定义。
    这种场景用错误码更稳妥。


六、老师傅的经验
----------------------------------------------------------------

1. 【先培养异常安全意识】
   不用上来就研究什么强保证弱保证。
   先养成一个习惯：
   写代码的时候，每申请一个资源，就想想：
   "如果后面抛异常了，这个资源能释放吗？"
   只要答案是"不确定"，就用 RAII 包起来。
   这个习惯养好了，80% 的异常安全问题就没了。

2. 【RAII 是 C++ 里最重要的思想之一】
   很多人学 C++ 只知道类、继承、多态，
   觉得 RAII 是个小技巧。
   大错特错。
   RAII 是 C++ 的灵魂。
   没有 RAII，异常根本没法用（到处泄漏）。
   没有 RAII，C++ 的内存管理就是灾难。
   理解了 RAII，你才算真正入了 C++ 的门。

3. 【异常不是越多越好】
   什么错都抛异常也不对。
   预期内的、频繁发生的错误，用错误码或者返回值更合适。
   比如"用户输入格式不对"，这是常态，不是异常。
   再比如"查数据库没查到"，这也很正常，返回空就行。
   异常应该用在"不正常"的情况：
   数据库连不上、文件损坏了、内存不够了……
   一句话：异常是给"意料之外"的错误用的。

4. 【关于 noexcept 的使用策略】
   新手常见问题："到底要不要标 noexcept？"
   简单原则：
     - 确定不抛的 → 标
     - 不确定的 → 不标
     - 移动构造/移动赋值 → 尽量标（性能影响大）
     - 析构函数 → 默认就是，不用手动写
     - swap → 通常标
   noexcept 是承诺，说到就要做到。
   做不到就别瞎承诺，不然崩给你看。

5. 【错误处理是设计出来的】
   不要等到代码写完了才想"错误怎么处理"。
   错误处理是架构设计的一部分，从一开始就要考虑：
     - 哪些地方可能出错？
     - 出了错谁来处理？
     - 用异常还是错误码？
     - 异常安全到什么级别？
   想清楚了再动手，比写完再补强得多。

6. 【多写多踩坑，自然就会了】
   异常安全这东西，光看没用。
   你得真写过几个泄漏的 bug，
   真调试过几个莫名其妙的崩溃，
   才会真正理解"为什么要这么做"。
   别怕踩坑，踩过的坑都是你的经验。
