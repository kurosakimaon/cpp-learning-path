# 单元测试学习指南

## 一、为什么要写单元测试？

很多初学者问："我手动运行一下看看结果不行吗？为什么非要写测试？"

行，当然行——在代码只有几十行、只有你一个人维护的时候。

但现实是：

- 项目会越来越大，函数会越来越多
- 你会改旧代码，你记不住所有影响
- 团队里有别人也在改代码
- 重构的时候，你需要信心

单元测试就是你的"安全网"，它的价值在于：

1. 回归保障：改了代码，跑一遍测试就知道有没有搞坏别的东西
2. 重构底气：没有测试的代码，你敢大改吗？改完怎么验证？
3. 活文档：好的测试用例就是最好的使用示例，比注释靠谱
4. 倒逼设计：难测的代码通常耦合重、职责不清，写测试能逼你拆
5. 减少调试时间：bug 被测试抓出来，比在生产环境排查快多了

一句话：测试不是浪费时间，是省时间。前期多花 20% 时间写测试，后期少花 200% 时间修 bug。

## 二、测试框架对比

C++ 里主流的单元测试框架有三个：Google Test、Catch2、doctest。

### Google Test（GTest/GTest）

- 最老牌、最流行、工业界标准
- 功能最全：参数化测试、死亡测试、测试夹具、XML 报告……
- 配合 Google Mock 做 Mock 也很方便
- 缺点：需要编译安装，宏定义比较多，学习曲线稍陡
- 适合：大型项目、企业级开发

### Catch2

- v2 是单头文件（一个 `catch.hpp` 就能用），上手极快；v3 已经拆成需要编译的库（`Catch2::Catch2WithMain`）
- 语法比较自然，BDD 风格（GIVEN/WHEN/THEN）
- 社区活跃，文档友好
- 缺点：v2 单头文件编译慢；某些高级功能不如 GTest
- 适合：中小型项目、快速原型、个人项目

### doctest

- 也是单头文件，比 Catch2 更轻、编译更快
- 语法和 Catch2 类似
- 设计目标是"最轻量的测试框架"
- 缺点：功能相对少一些，社区不如前两个大
- 适合：对编译速度敏感的项目、嵌入式开发

### 怎么选？

- 公司项目/团队开发 → Google Test（行业标准，大家都熟）
- 个人项目/快速上手 → Catch2（写起来舒服）
- 极致轻量 → doctest

本教程用 Google Test，因为它是工业界的事实标准，学会了 GTest，到哪都能用。

### 重要提醒

本目录的两个示例为了演示 ASSERT/EXPECT 的区别、自定义失败信息和 SCOPED_TRACE，故意保留了会失败的测试用例（文件头有标注），一共 4 个：

- `01_gtest_basics.cpp`:
  - `AssertVsExpectTest.DemonstrateDifference`
  - `CustomMessageTest.ShowCustomInfoOnFailure`
- `02_gtest_advanced.cpp`:
  - `ScopedTraceTest.HelpsDebugLoopFailures`
  - `ScopedTraceTest.WorksInHelperFunctions`

所以直接跑会看到少量失败，这是教学效果，不是代码坏了。想跳过这四个用例，可以这样过滤（同一个过滤器里用 `:` 分隔）：

```text
--gtest_filter=-AssertVsExpectTest.DemonstrateDifference:CustomMessageTest.ShowCustomInfoOnFailure:ScopedTraceTest.HelpsDebugLoopFailures:ScopedTraceTest.WorksInHelperFunctions
```

## 三、怎么学？学习路径

建议按顺序来，不要跳：

### 第 1 步：01_gtest_basics.cpp —— 入门基础

- `TEST` 宏怎么写
- 各种断言怎么用
- `ASSERT` 和 `EXPECT` 的区别
- `TEST_F` 测试夹具
- 看完能写基本的测试用例

### 第 2 步：02_gtest_advanced.cpp —— 进阶技巧

- 参数化测试（写一组数据跑 N 个用例）
- 死亡测试（测"程序应该崩"的场景）
- `SCOPED_TRACE` 调试技巧
- Mock 概念（用假依赖测真逻辑）
- TDD 思想（测试驱动开发）

### 第 3 步（自学）：Google Mock（gmock）

- 进阶的 Mock 框架
- `EXPECT_CALL`、`Times`、`WillOnce` 等
- 真实项目里 Mock 是刚需

### 第 4 步（自学）：测试覆盖率工具

- gcov + lcov 或者 OpenCppCoverage
- 看看哪些代码没被测到

每学完一个文件，把小练习做了。光看不练假把式。

## 四、好测试的标准（F.I.R.S.T. 原则 + 可读性）

业界有个 F.I.R.S.T. 原则，说好的单元测试应该满足：

- F - Fast（快速）  
  测试要跑得快，慢了大家就不想跑了。毫秒级的单元测试才叫单元测试，要几秒几分钟的那叫集成测试。

- I - Independent / Isolated（独立）  
  测试之间互不依赖，A 测试失败不影响 B 测试。每个测试自己准备数据、自己清理。不要假设测试执行顺序。

- R - Repeatable（可重复）  
  同样的代码跑 100 次，结果应该一样。不要依赖外部环境（网络、数据库、系统时间）。随机行为要有办法控制。

- S - Self-validating（自验证）  
  测试自己判断对错，不需要人去看输出说"好像对了"。断言要明确，pass 就是 pass，fail 就是 fail。

- T - Timely（及时）  
  最好和业务代码一起写，甚至先写测试（TDD）。代码写完了再补测试，往往就懒得补了。

老师傅再加两条：

- R - Readable（可读）  
  测试代码也是代码，也要让人看得懂。好的测试用例，看名字就知道测啥。命名建议：测试的功能 + 场景 + 预期结果  
  比如：`add_TwoPositiveNumbers_ReturnsSum`

- O - One assertion per test（尽量一个测试只测一件事）  
  一个测试里堆一堆断言，第一个失败了后面都看不到。分开写，哪个失败一目了然。

## 五、测试覆盖率

测试覆盖率 = 被测试执行过的代码 / 总代码

常见的覆盖率指标：

- 行覆盖率（Line Coverage）：多少行代码被执行过
- 分支覆盖率（Branch Coverage）：每个 if 的两个分支都走到了吗
- 函数覆盖率（Function Coverage）：每个函数都被调用过吗

行覆盖率最常用，但也是最"水"的。100% 行覆盖率不代表代码没问题，因为一行代码可能有很多种执行路径。

### 覆盖率多少算够？

没有标准答案，看项目要求。

- 一般来说，70%~80% 就不错了
- 核心模块、底层库应该更高，90%+
- 100% 通常不值得追求（边际效益递减）

记住：覆盖率是手段，不是目的。不要为了凑覆盖率写没有意义的测试。比起数字，更重要的是"关键路径和边界条件都测到了吗"。

## 六、TDD 是什么，要不要学？

TDD = Test-Driven Development，测试驱动开发。

核心循环：红 → 绿 → 重构

- 红：先写测试，跑不过（红色失败）
- 绿：写最少的代码让测试通过（绿色通过）
- 重构：优化代码结构，保持测试还是绿的

### TDD 的好处

1. 需求先行：逼你想清楚"要什么"再写"怎么做"
2. 设计驱动：难测的代码设计通常不好，TDD 逼你解耦
3. 安全感：每一步都有测试兜底，步子可以迈得大一点
4. 天然文档：测试就是最好的使用示例

### TDD 的争议

1. 前期慢：先要写一堆测试，才能开始写业务代码
2. 不适合所有场景：比如探索性开发、UI 开发
3. 学习成本高：新手容易走火入魔，为了 TDD 而 TDD

### 老师傅的建议

学，一定要学——哪怕你不完全按它来。TDD 的思维方式比流程更重要："写代码之前先想怎么测"、"接口设计要站在使用者角度"。

实际工作中，不用死磕"每一行代码都必须 TDD"。核心逻辑、复杂算法、容易出 bug 的地方，用 TDD。简单的胶水代码、一次性脚本，没必要。

关键是：测试要写，而且要写好。

## 七、老师傅的经验之谈

### 1. 测试代码也是代码

别觉得测试代码就可以乱写。命名、结构、复用性，一样重要。测试代码烂了，维护成本比业务代码还高。

### 2. 别测实现，测行为

好的测试关心"输入输出对不对"，不关心"内部是怎么实现的"。你把冒泡排序改成快速排序，测试应该不用改，结果一样对。如果测试依赖内部实现，那一重构就得改测试，累不累？

### 3. 边界条件是 bug 高发区

0、空、null、最大值、最小值、重复数据……这些地方最容易出问题。写测试的时候，多想想"极端情况"。

### 4. 测试不是越多越好

一个永远不会失败的测试，毫无价值。一个失败了你也不知道为啥的测试，不如不写。质量 > 数量。

### 5. 集成测试也很重要

单元测试是基础，但不是全部。模块之间的配合、系统整体的流程，也需要测。单元测试 + 集成测试 + 端到端测试，是一个金字塔。单元测试最多最快，越往上越少越慢。

### 6. 不要为了测试而测试

测试是工具，不是目的。目的是写出可靠、可维护的代码。如果一个东西测起来特别费劲，可能不是测试的问题，是代码设计的问题。

### 7. 从现在开始，从一个函数开始

不要等"项目大了再写测试"，那时候你更不会写。从今天起，写新函数的时候顺手写两个测试。习惯了就好。
