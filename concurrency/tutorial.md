# 并发编程专题

> C++ 里最容易出 bug 也最难调试的领域

## 一、模块简介

徒弟啊，并发编程这玩意儿，师傅跟你说实话：
这是 C++ 里水最深的一块。

为什么这么说？因为并发的 bug 有几个特点：

- 不一定每次都出现（偶现）
- 加个打印就没了（Heisenbug）
- 本地复现不了，线上必崩
- 查起来跟破案似的，线索少得可怜

所以并发这东西，能不用就不用。
但真要用的时候，你得心里有数。

这个模块从线程基础讲到进程间通信，
一共 7 个文件，带你把并发这块搞明白。

## 二、学习目标

学完本模块，你要能做到：

1. 会用 `std::thread` 创建和管理线程
2. 掌握常用同步原语（`mutex`、`lock`、`condition_variable`）
3. 理解竞态条件和死锁，知道怎么避免
4. 了解原子操作和内存序（知道 `seq_cst` 默认够用）
5. 知道线程池的原理和使用场景
6. 会用 `async`/`future` 做简单的异步任务
7. 了解常见的进程间通信方式

## 四、学习顺序建议

师傅给你划条线，按顺序来：

### 第一步：线程基础（01）

先搞明白怎么创建线程、怎么等待线程结束、
怎么给线程传参。这是基础中的基础。

重点注意：`detach` 要慎用，`join` 要确保一定调用。
不然要么线程崩了主程序不知道，要么程序直接 terminate。

### 第二步：同步原语（02）

多个线程访问共享数据，就得同步。
`mutex` 是最基本的，`lock_guard` 和 `unique_lock` 是 RAII 包装。
`condition_variable` 用来做线程间的等待通知。

这一节要多动手写例子，体会一下"为什么需要锁"。

### 第三步：竞态与死锁（03）—— 重中之重

这一节是整个并发模块的核心。
不理解竞态条件，你写的并发代码就是在埋雷。
不理解死锁，你写的程序哪天就卡住了。

一定要搞懂：

- 竞态条件是怎么发生的（`i++` 为什么不是原子的）
- 死锁的四个必要条件
- 怎么避免死锁（锁顺序、RAII、超时……）

### 第四步：原子操作（04）

原子操作是无锁编程的基础。
但师傅提醒你：内存序这东西很深，
`seq_cst`（默认）就够 99% 的场景用了。
别上来就折腾 `relaxed`、`acquire-release`，
那玩意儿一般人搞不定。

### 第五步：线程池与 async（05~06）

实际项目中，你很少直接裸用 `thread`，
一般都是用线程池或者 `async`。
这两个是更高级的抽象，用起来更方便，也更安全。

### 第六步：进程间通信（07）

进程间通信（IPC）是另一个话题了。
了解一下常见的方式就行，
真要用到的时候再深入研究。

## 五、核心知识点梳理

咱挑最核心的说：

### 1. 竞态条件（Race Condition）

多个线程同时访问共享数据，
而且至少有一个是写操作，
结果依赖于线程的执行顺序，
这就是竞态条件。

最简单的例子：两个线程同时对一个全局变量 `i++`。
`i++` 不是一条 CPU 指令，是三步：
读 → 加一 → 写回。
两个线程交错执行，就可能丢一次加一。

解决方法：加锁，或者用原子操作。

### 2. 死锁的四个必要条件

- 互斥：资源不能共享，一次只能一个线程用
- 占有并等待：线程拿着一个锁，等另一个锁
- 不可剥夺：锁不能被强行抢走，只能主动释放
- 循环等待：A 等 B 的锁，B 等 A 的锁

四个条件同时满足才会死锁。
打破任意一个，死锁就不会发生。
最常用的方法：保证所有线程按相同顺序加锁。

### 3. mutex 不是万能的

加锁能解决竞态问题，但也带来新问题：

- 性能：锁的开销不小，竞争激烈的时候更慢
- 死锁：加锁顺序不对就死锁
- 优先级反转：高优先级线程等低优先级的锁

所以能不加锁就不加锁，
能少加锁就少加锁。

### 4. 为什么要有 condition_variable

你想等某个条件成立，怎么办？
轮询？太浪费 CPU 了。
`condition_variable` 就是干这个的：
条件不满足就等着，条件满足了别人通知你。
不占 CPU，效率高。

### 5. 线程池为什么好

每次创建线程都有开销，
任务多了线程太多，调度开销也大。
线程池就是预先创建好一堆线程，
任务来了就分配给空闲线程，
任务完了线程不销毁，等着下一个任务。

既减少了线程创建销毁的开销，
又控制了并发数量，避免系统过载。

## 六、常见坑与注意事项

### 1. 忘了 join 或 detach

`std::thread` 对象销毁的时候，
如果线程还在运行（既没 `join` 也没 `detach`），
程序直接 terminate，崩给你看。
一定要确保 `join` 或 `detach` 被调用。

### 2. 死锁

两个锁，A 线程先锁 1 再锁 2，
B 线程先锁 2 再锁 1。
跑着跑着就卡住了。
解决方法：所有线程按相同顺序加锁。

### 3. 假唤醒（Spurious Wakeup）

`condition_variable` 的 `wait` 可能会"无缘无故"醒来。
所以 `wait` 一定要配合循环使用：

```cpp
   while (!条件) cv.wait(lock);
```

醒来了再检查一遍条件，不满足继续等。

### 4. 共享数据没全加锁

一个变量，有的地方加锁读，有的地方不加锁写，
等于没加锁。所有访问共享数据的地方都要加锁。

### 5. 内存序乱选

原子操作的内存序有好几种，
别为了"性能优化"乱选 `relaxed`。
默认的 `seq_cst` 约束最强、通常开销更大（但不保证所有平台都更慢），
但最安全、最不容易写错。
你真的需要别的内存序的时候，
你自然就知道了。不知道的时候，就用默认的。

## 七、老师傅的经验之谈

### 1. 能不用多线程就不用

徒弟，这是师傅掏心窝子的话：
能不用多线程就不用。

很多时候，单线程 + 事件循环（比如 Node.js 那种模式）
比多线程可靠多了，也好调试多了。
I/O 密集型的任务，异步 I/O 比多线程香。

什么时候才需要多线程？
CPU 密集型任务，要榨干多核性能的时候。
或者必须同时做几件互相阻塞的事的时候。

### 2. 并发 bug 是最难调试的

并发的 bug 有个外号叫"海森堡 bug"（Heisenbug），
意思是你一观察它，它就消失了。
加个打印、加个断点，bug 就不复现了。
因为打印和断点会改变线程的执行时序。

所以写并发代码，一定要慎之又慎。
设计的时候就想清楚同步策略，
别写完了再去 debug，那会很痛苦。

### 3. 锁的粒度很重要

锁太粗（一个大锁保护所有数据），
并发度低，性能上不去。
锁太细（每个变量一个锁），
容易死锁，也不好维护。

找到合适的粒度，是门艺术。

### 4. 优先用高级抽象

能不用裸 `thread` 就不用，
优先用线程池、`async/future` 这些高级抽象。
能不用 `mutex` 就不用，
优先用消息队列、并发容器这些封装好的东西。

抽象层次越高，越不容易出错。

### 5. 测试很重要，但也很不够

并发程序很难靠测试保证正确性。
你跑一万次都没问题，第一万零一次可能就崩了。
所以更重要的是设计正确，而不是测试通过。

当然，测试还是要做的。
压力测试、长时间运行测试，都是必要的。
