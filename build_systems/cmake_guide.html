〇、怎么用这一页

这页不是 CMake 语法课——语法在 cmake_01～cmake_06 六个示例的 tutorial.md 里逐个讲。这页只解决三件事：

  1. 命令怎么敲：把散在各教程里的命令收成一张表；
  2. 每步该看到什么：配置输出哪几行、构建输出哪几行、产物落在哪个目录；
  3. 报错了怎么查：按报错原文定位原因，不用猜。

用法：先照 三步固定动作 把 cmake_01_basic 跑通， 之后每学一个示例，就到 六个示例逐条对照 找到它那一节， 对着「该看到的输出」核一遍。对不上，就去 报错对照表。

关于本页的"预期输出"有多可信： 本页输出的项目相关内容（-- 构建类型：Debug、[100%] Built target hello、 测试名 CalculatorTest 等）是从本仓库各 CMakeLists.txt 里实际写的 message()、add_executable()、add_test() 抄出来的，不会变。 而与机器相关的行（编译器版本号、生成器名、绝对路径、百分比分档） 按 MinGW/Makefiles + CMake 3.15+ 的通用格式给出，你的机器上措辞可能略有差异。 这台开发机目前没装 CMake，所以本页尚未在本机实跑对照过——装好后第一件事就是回来核这几行。

一、三步固定动作

CMake 干的事永远只有三件，任何项目都是这三步：

步骤命令干什么产物
① 配置
configure		 cmake -S . -B build 读 CMakeLists.txt，找编译器，生成构建系统 build/CMakeCache.txt、build/Makefile 或 build/*.vcxproj
② 构建
build		 cmake --build build 调用底层生成器真正编译链接 可执行文件、.a/.lib/.dll
③ 运行/安装 ./build/hello
cmake --install build		 跑起来看结果；或按 install() 规则拷到 CMAKE_INSTALL_PREFIX 安装目录下的 bin/、lib/、include/
为什么永远用 -B build（out-of-source）： 构建产物全在 build/ 里，想重来就整个删掉，源码目录一个脏文件都不留。 老教程里 mkdir build && cd build && cmake .. 是同一个意思， -S . -B build 是新版写法，不用 cd。

删掉重来（改了 CMakeLists.txt 后行为诡异时用）：

# 方式一：整个目录推倒重来，最干净
cmake -S . -B build --fresh

# 方式二：手动删（Windows PowerShell）
Remove-Item -Recurse -Force build
# 手动删（Git Bash / Linux）
rm -rf build

配置只需一次，之后改代码只跑第 ② 步就行——CMake 会在构建时自动检测 CMakeLists.txt 是否变化并重新配置。

二、命令速查

配置阶段

命令作用
cmake -S . -B build用默认生成器配置到 build/
cmake -S . -B build -G "MinGW Makefiles"指定生成器（Windows 上想用 make 就这个）
cmake -S . -B build -G Ninja用 Ninja（快，需另装 ninja）
cmake -S . -B build -G "Visual Studio 17 2022"生成 VS 解决方案（多配置生成器）
cmake --list-presets / --preset 名字列出并使用 CMakePresets.json 里配好的组合
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug传变量：-D名=值，等价于在 CMakeLists 里 set 缓存变量
cmake -S . -B build -DCMAKE_INSTALL_PREFIX=../out指定安装前缀，install() 的目标目录都相对它
cmake -S . -B build --fresh忽略旧缓存，干净重配
cmake --build build --target help列出生成器里所有可构建目标（Makefile 生成器下有效）

构建阶段

命令作用
cmake --build build构建全部默认目标（生成器无关，永远能用）
cmake --build build --target hello只构建某个目标
cmake --build build --config Release多配置生成器（VS/Xcode）选配置；单配置生成器用 -DCMAKE_BUILD_TYPE
cmake --build build -j 8并行 8 个任务（CMake 3.12+）
cmake --build build -- VERBOSE=1打印每条真实调用的编译命令（Makefile 生成器）；VS 下用 -- /v:detailed
cmake --build build --clean-first先清理再构建

装 / 测 / 查

命令作用
cmake --install build执行安装（CMake 3.15+；旧版用 cmake --build build --target install）
cmake --install build --prefix ../out临时改安装目录
ctest --test-dir build跑测试（CMake 3.20+；旧版先 cd build 再 ctest）
ctest -N / -V / --output-on-failure / -R 正则 / -j4只列出 / 详细 / 失败才输出 / 按名字筛 / 并行
cmake -LH（在 build 目录里）列出缓存变量及其 help 字符串——查"-D 到底生效没有"最好用
ccmake -S . -B buildncurses 图形界面改缓存（Windows 需装 cmake-curses-gui）
cmake --graphviz=deps.dot -S . -B build导出目标依赖图，配合 Graphviz 看链接关系
两个最容易记混的点： ① --config 只对 VS/Xcode 这类多配置生成器有意义； Makefile/Ninja 是单配置，配置时在 configure 阶段用 -DCMAKE_BUILD_TYPE= 定死。 ② -D 传的是缓存变量，写错名字不报错、只是没效果——所以传完用 cmake -LH 确认。

cmake_02_multi_file · 多个源文件
main.cpp + utils.cpp/.h + math.cpp/.h，目标 demo；用变量 SOURCES 收拢源文件列表
cmake -S . -B build

该看到什么

[  25%] Building CXX object CMakeFiles/demo.dir/main.cpp.obj

cmake_04_options · 选项、configure_file、构建类型
工程 OptionsDemo 版本 1.2.3；两个开关 ENABLE_DEBUG_OUTPUT、ENABLE_EXPERIMENTAL_FEATURES 默认都是 OFF；config.h.in → build/config.h

cmake -S . -B build
cmake --build build
./build/options_demo

# 打开调试输出这个开关
cmake -S . -B build -DENABLE_DEBUG_OUTPUT=ON
cmake --build build
./build/options_demo        # 会多出 [DEBUG] 计算 ... 那些行

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release

该看到的配置输出（本项目自己的 message）

-- 构建类型：Debug
-- 调试输出：OFF
-- 实验功能：OFF
-- Configuring done
-- Generating done

把 -DENABLE_DEBUG_OUTPUT=ON 加上后，同样三行变成 -- 调试输出：ON，且运行程序时会打印 [DEBUG] 计算 3 + 4 = 7 这类行。

程序里该看到什么

  项目名称：OptionsDemo
  项目版本：1.2.3
  构建类型：Debug
  作者：老师傅和徒弟

这四行来自 config.h.in 被 configure_file() 替换的结果—— @PROJECT_NAME@、@PROJECT_VERSION@、@CMAKE_BUILD_TYPE@、@AUTHOR_NAME@。 生成的文件在 build/config.h，打开它亲眼看一次比读十遍说明有用。

四、PRIVATE / PUBLIC / INTERFACE 一张表

这三个词只回答一个问题：我用的这个东西，要不要传染给链接我的人？

关键字我自己编译时用链接我的人用典型场景
PRIVATE✅❌实现细节：内部依赖的库、只给自己用的头文件目录
PUBLIC✅✅出现在公开头文件里的东西：mathlib 的 include 路径、cxx_std_17
INTERFACE❌✅纯头文件库（header-only）、只给使用者的编译选项

拿本仓库的例子对照：mathlib/CMakeLists.txt 里写

target_include_directories(mathlib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
target_link_libraries(math_app        PRIVATE mathlib)

第一行的 PUBLIC 意思是"这个头文件目录是我的公开接口的一部分"， 所以第二行 math_app 即使没有自己写 include_directories， 也能 #include "math_functions.h"——路径是跟着 mathlib 传染过来的。 把 PUBLIC 改成 PRIVATE 再构建一次，你会立刻在 math_app 那一步看到 fatal error: math_functions.h: No such file or directory。 这一改一报，比背下表管用。

全局命令 include_directories() / link_libraries() / add_definitions() 会污染整个目录树，现代 CMake 一律改用 target_* 形式。本仓库根 CMakeLists.txt 里刻意没有全局 include 路径， 就是这个原因。

五、报错对照表

报错原文（关键片段）真实原因怎么修
No CMAKE_CXX_COMPILER could be found / No C compiler PATH 里找不到编译器，或 VS 工作负载没装 C++ MSYS2：把 C:\msys64\ucrt64\bin 加进 PATH；VS：安装"使用 C++ 的桌面开发"；再 cmake -S . -B build --fresh
Error: generator : MinGW Makefiles
Does not match the one used to ... 		build/ 里存着别的生成器留下的缓存 删掉 build/ 重来，或 --fresh。缓存与生成器绑定，不能中途换
The source directory ... does not appear to contain any CMakeLists.txt -S 指错目录（比如指到了 build_systems/ 而不是某个 cmake_0x/） 到含 CMakeLists.txt 的那一层再敲；六个示例各自独立，不能在 build_systems/ 顶层配置
undefined reference to `xxx`（MSYS2/Linux）
unresolved external symbol（MSVC）		 源文件没进 add_executable，或依赖的库没 target_link_libraries 把实现所在的 .cpp 加进目标源文件列表；库目标加进 target_link_libraries。这是 cmake_02/03 最常见的坑
fatal error: xxx.h: No such file or directory 缺 target_include_directories，或者库那边写成了 PRIVATE 见上一节：公开头文件所在目录要用 PUBLIC
CMake Error: ... requires CMake <version> or higher 本机 CMake 低于 cmake_minimum_required（cmake_05/06 要求 3.15） 升级 CMake；cmake --version 先看一眼
Could NOT find Boost (missing: ...) 或本仓库根构建时 Boost 示例被跳过 没装 Boost，或 find_package(Boost ...) 找不到；根 CMakeLists.txt 用的是 QUIET COMPONENTS，找不到就静默跳过那些示例 装 Boost 或加 -DBOOST_ROOT=...；想知道到底找到没有，用 cmake -LH | grep -i boost
ctest 报 No tests were found!! 根 CMakeLists.txt 里没有 enable_testing()，或它写在 add_subdirectory(tests) 之后；也可能是 -DBUILD_TESTS=OFF enable_testing() 必须在根、且在 add_subdirectory(tests) 之前（cmake_06 就是这么写的）
cannot find -lboost_thread（本仓库 Boost 示例） MSYS2 的库名带 -mt 后缀 手动编译时用 -lboost_thread-mt；用 CMake 时交给 find_package(Boost COMPONENTS thread) 处理
改了 CMakeLists.txt 但行为没变 缓存里还留着旧值，尤其 -D 传过的变量 cmake -LH 看当前值；--fresh 或删 build/ 强制重来
Windows 运行 exe 报"找不到 libstdc-6.dll" exe 依赖 MSYS2 的运行时 DLL，而它不在 PATH 把 C:\msys64\ucrt64\bin 加进 PATH 再运行（这是环境 PATH 问题，不是代码问题）
install 报权限错误 默认前缀是 C:/Program Files 永远用 --prefix 指到项目内目录，例如 cmake --install build --prefix ../out

👴 老师傅的话

徒弟，CMake 这东西，刚上手会觉得它啰嗦：target_ 开头的一串命令，写个 hello world 要七八行。

但你换个角度想——CMake 不是"构建工具"，它是描述工具。你写的不是"先编译这个再编译那个"， 而是"这个可执行文件依赖那个库，那个库的公开接口包含这些头文件"。依赖关系一描述清楚， 谁先谁后、并行几个、要不要重编，CMake 自己算。这就是为什么它能跨平台，而手写的 Makefile 不能。

师傅给你三条规矩，照着做少踩九成坑：

  • 永远 out-of-source：-S . -B build，别在源码目录里配置。想重来就删 build/，源码永远干净。
  • 能用 target_* 就不用全局命令：include_directories、link_libraries、add_definitions 这些全局货，写的时候爽，项目一大就是灾难。
  • 链接别人家库，一律写 名字::名字：Boost::filesystem、mathlib::mathlib。带 :: 的拼错了当场报错，不带的可能悄悄链到别的东西上。

最后一句：别背命令，去改一行看反应。把 PUBLIC 改成 PRIVATE， 把 enable_testing() 挪个位置，把 option(...) 的默认值翻过来—— 看它报什么错、少生成什么文件。CMake 的手感是这么来的，看文档看不出来。
