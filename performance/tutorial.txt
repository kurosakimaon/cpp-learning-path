【一、模块简介】

徒弟啊，欢迎来到性能优化专题。

很多人一提到性能优化，就想到各种奇技淫巧、
汇编级别的微调。但师傅告诉你，那都是末节。

真正的性能优化，90% 的收益来自于：
  1. 选对算法和数据结构
  2. 写出缓存友好的代码
  3. 避免常见的性能陷阱
  4. 找准瓶颈，集中火力

这个模块就带你打好性能优化的基础，
从理解 CPU 缓存开始，到识别常见陷阱，
再到学习正确的优化方法论。

记住：性能优化不是玄学，是科学。
用工具测量，用数据说话。


【二、学习目标】

学完本模块，你要能做到：

  1. 理解 CPU 缓存的工作原理（L1/L2/L3、缓存行）
  2. 知道什么是空间局部性、时间局部性
  3. 能写出缓存友好的代码（行优先遍历、结构体对齐等）
  4. 识别并避免 6 种以上常见的性能陷阱
  5. 掌握用 <chrono> 做基准测试的方法
  6. 建立"先测量再优化"的正确观念


【三、文件列表与学习重点】

咱一共 2 个源文件，都是干货：

  01_cache_optimization.cpp    ← 缓存与内存优化
    重点：CPU 缓存原理、行优先 vs 列优先、
          结构体对齐、数组 vs 链表、AOS vs SOA
    难度：中级
    建议：每个实验都亲手跑一遍，看看你的机器上差多少

  02_common_pitfalls.cpp       ← 常见性能陷阱
    重点：对象拷贝、隐式转换、虚函数开销、
          string 拼接、vector 扩容、shared_ptr 原子开销
    难度：中级
    建议：对照自己的代码，看看有没有踩这些坑


【四、学习顺序建议】

师傅建议你这么学：

【第一步：学缓存优化（01_cache_optimization.cpp）】
  这是性能优化的基石。
  理解了缓存，你对性能的认识会上升一个层次。

  重点掌握：
  - 为什么行优先比列优先快
  - 结构体为什么会有 padding
  - 数组为什么比链表快（不只是算法复杂度的问题）
  - SOA 是什么，什么时候用

  每个实验都跑一遍，别光看。
  你会发现，同样的逻辑，不同的写法，
  性能差距可能有好几倍。

【第二步：学常见陷阱（02_common_pitfalls.cpp）】
  知道了什么是快的，还要知道什么是慢的。
  这些陷阱都是日常开发中最容易踩到的。

  学的时候要想：
  - 我自己的代码里有没有这样的写法？
  - 这个陷阱的代价有多大，值不值得改？
  - 有没有更好的写法？

【第三步：养成习惯】
  性能优化不是学完就完了，
  要把这些知识融入到日常编码中。

  写代码的时候多想想：
  - 这个参数该不该传引用？
  - 这个 vector 要不要 reserve？
  - 这个循环的内存访问模式友好吗？

  时间长了，你写出来的代码天然就是快的。


【五、性能优化的核心原则】

1. 【先测量，再优化】
   这是第一原则，也是最重要的原则。
   永远不要猜哪里慢，用工具测！
   你以为的瓶颈，90% 的概率不是真正的瓶颈。

2. 【Amdahl 定律】
   优化一个部分，能带来多少整体提升，
   取决于这个部分占总时间的比例。

   公式：总加速比 = 1 / ((1 - p) + p / s)
   其中 p 是被优化部分占总时间的比例，s 是该部分的加速比。

   举个例子：
   某函数占总时间的 10%，你把它优化了 2 倍，
   总速度提升只有 5% 左右，不值得花大力气。
   但如果某函数占 80%，你把它优化 2 倍，
   总速度提升接近 50%，收益巨大。

   所以，优化要找热点，别在冷门代码上浪费时间。

3. 【80/20 法则】
   80% 的运行时间花在 20% 的代码上。
   找到那 20% 的热点，集中火力优化。

4. 【正确性优先】
   优化的前提是代码是正确的。
   为了快几毫秒把代码改出 bug，得不偿失。

5. 【可读性优先】
   除非性能真的很关键，否则别为了快
   把代码写得晦涩难懂。
   好维护比快几毫秒重要得多。


【六、常用性能分析工具】

工欲善其事，必先利其器。
以下是常用的性能分析工具，知道有这些东西，
需要的时候知道去查就行：

1. 【Linux 平台】
   - perf：Linux 官方性能分析工具，功能强大
     perf record ./program   # 记录性能数据
     perf report             # 查看报告
   - valgrind --callgrind：调用图分析
   - gprof：GNU 性能分析工具（比较老了）

2. 【火焰图（Flame Graph）】
   - 非常直观的性能可视化工具
   - 宽的方块表示占时间多，一眼就能看到热点
   - 通常和 perf 配合使用
   - 搜索 "FlameGraph Brendan Gregg" 就能找到

3. 【Windows 平台】
   - Visual Studio 性能探查器：自带的，很好用
     支持 CPU 采样、内存分析、并发分析等
   - Very Sleepy：轻量级的 CPU 采样工具

4. 【跨平台】
   - Google Benchmark：写基准测试的库
   - Tracy：实时性能分析工具（游戏开发常用）

5. 【最简单的工具：<chrono>】
   - 就是本课程用的方法
   - 不需要额外安装，标准库自带
   - 适合测一小段代码的性能
   - 但要注意：测整体瓶颈还是要用专业工具


【七、常见误区】

1. 【过早优化】
   "过早优化是万恶之源。" —— Donald Knuth
   在你还不知道瓶颈在哪里的时候就开始优化，
   往往是白费功夫，还把代码搞复杂了。
   先写正确，再测性能，最后优化。

2. 【过度优化】
   把一个只占总时间 1% 的函数优化了 50%，
   总速度提升 0.5%，有意义吗？
   优化是有成本的（时间、复杂度、可读性），
   要权衡收益和代价。

3. 【微观优化】
   纠结于 i++ 和 ++i 哪个快，
   纠结于用位运算代替乘除法……
   这些都是编译器已经帮你做好的事。
   现代编译器的优化能力远超你的想象，
   别在这些地方浪费时间。

4. 【只看时间复杂度】
   很多人觉得 O(n) 一定比 O(n log n) 快，
   其实不一定。常数因子也很重要。
   一个缓存友好的 O(n log n) 算法，
   可能比缓存不友好的 O(n) 算法快得多。
   （比如二叉搜索 vs 线性搜索，数据量小的时候线性搜索反而快）

5. 【凭感觉优化】
   "我觉得这里慢。"
   你觉得不算，数据才算。
   永远用工具测量，别凭感觉。


【八、怎么学好性能优化】

师傅给你指条路：

1. 【理解底层】
   先搞懂 CPU、缓存、内存是怎么工作的。
   不理解硬件，谈性能优化都是空中楼阁。

2. 【学会测量】
   熟练使用至少一个性能分析工具。
   遇到性能问题，第一步永远是测量。

3. 【多写多练】
   看十篇文章，不如自己写个 benchmark 跑一遍。
   自己测出来的数据，印象才最深。

4. 【读优秀代码】
   看看那些高性能的开源项目是怎么写的，
   比如 Google 的代码、LLVM、游戏引擎……
   你会学到很多实用技巧。

5. 【保持好奇】
   遇到慢的代码，多想为什么慢。
   是算法问题？内存问题？还是 I/O 问题？
   找到原因，你就进步了。


【九、老师傅的经验之谈】

1. 【性能是设计出来的，不是调出来的】
   徒弟啊，很多人以为性能优化是：
   代码写完了，跑一遍，发现慢，然后去调。
   不对！真正的高性能，是从设计阶段就决定的。

   架构选错了、数据结构选错了、访问模式选错了，
   后期再怎么调都是杯水车薪。
   所以，写代码之前先想想：
   这个功能对性能要求高不高？
   数据量有多大？
   用什么数据结构最合适？
   访问模式是怎样的？

   设计阶段多花 1 小时，
   可能省掉后期 100 小时的优化时间。

2. 【大多数性能问题，都是内存问题】
   你学了缓存那一章就会明白，
   现代 CPU 的运算速度极快，
   真正的瓶颈往往在内存访问上。

   所以性能优化，很多时候就是在优化内存：
   - 让数据更紧凑（减少 padding、压缩）
   - 让访问更连续（数组代替链表）
   - 让缓存更有用（局部性优化）
   - 减少内存分配（对象池、预留空间）

3. 【别迷信"技巧"】
   网上有很多"C++ 性能优化 100 条"之类的文章，
   里面很多都是过时的或者不重要的。

   师傅告诉你，真正重要的就那么几条：
   - 选对数据结构
   - 写出缓存友好的代码
   - 避免不必要的拷贝和分配
   - 减少热点路径上的开销
   - 其他都是细枝末节

4. 【性能优化是一种思维方式】
   学性能优化，不是为了记住一堆技巧，
   而是培养一种思维习惯：
   写代码的时候，脑子里会想"这会不会慢？"
   遇到慢代码的时候，会想"为什么慢？"
   有了这种思维，你写出来的代码质量会越来越高。

5. 【别钻牛角尖】
   最后师傅提醒你一句：
   性能优化很有意思，但也容易上瘾。
   别为了抠那 1% 的性能，花一个星期去调。
   大多数时候，代码的可读性和可维护性更重要。

   记住：够用就好。
   只有当性能真的成为瓶颈的时候，再去优化。
